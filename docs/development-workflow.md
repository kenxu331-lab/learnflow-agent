# LearnFlow Agent 开发流程

每个模块都遵循以下顺序：

```text
需求确认 → 技术方案 → Codex 编码 → 自动化测试 → 代码审查 → 人工验收 → Git 提交与 PR → 技术复盘
```

流程的目的，是让每个模块都有明确边界、可重复验证的结果和可追溯的技术决策。没有完成测试与验收的模块，不能标记为“正式完成”。

## 阶段定义

### 1. 需求确认

进入条件：有明确的模块编号、目标、范围和验收标准。

执行要求：确认输入、输出、非目标、依赖和风险；检查当前分支与工作区，避免覆盖已有修改。

完成标准：任务边界和验收条件可以被开发者、Codex 和审查者共同理解；不明确的关键授权或范围问题已报告。

开发者职责：确认业务意图和优先级，提供必要的样例、约束和人工验收条件。

### 2. 技术方案

进入条件：需求边界已确认，且已阅读相关代码、配置、测试和架构文档。

执行要求：设计模块边界、核心接口、数据流、错误处理、测试策略和安全约束；评估是否需要新依赖或 ADR。

完成标准：方案与当前仓库架构一致，变更范围可控；重要取舍和未决问题已记录。

开发者职责：确认方案满足长期维护和隐私要求；对新增依赖、权限或外部服务作出明确决策。

### 3. Codex 编码

进入条件：方案可执行，目标分支和工作区状态已确认。

执行要求：只修改当前模块所需文件，优先复用现有实现，保持接口和命名清晰；不以占位代码冒充完成能力。

完成标准：代码实现了已确认范围，并能被静态检查和自动化测试覆盖。

开发者职责：及时回答会改变范围或安全边界的问题，审查关键实现而不是只关注最终输出。

### 4. 自动化测试

进入条件：代码已形成可运行的最小实现。

执行要求：按修改范围运行后端 Ruff/pytest 或扩展 typecheck/lint/build；新增功能必须有适当测试，记录真实输出、警告和失败原因。

完成标准：必要检查通过，或已明确记录阻塞项、未覆盖范围和下一步；失败测试不得被隐藏或伪造为成功。

开发者职责：补充业务边界和回归测试，判断测试是否真正验证验收标准。

### 5. 代码审查

进入条件：自动化测试完成并有可审查的差异。

执行要求：检查模块边界、错误处理、安全隐私、依赖变化、敏感文件、格式和测试断言；运行 `git diff --check`。

完成标准：没有未解释的阻塞性问题，审查意见已修复或明确接受风险。

开发者职责：验证行为和架构，而不只检查代码风格；确认变更没有混入其他模块。

### 6. 人工验收

进入条件：自动化检查通过，且存在需要真实环境验证的场景。

执行要求：按照验收清单执行实际服务、浏览器或外部工具检查，区分自动化结果和人工观察结果。

完成标准：验收场景有明确的通过、失败或未验证结论；不能操作的环境必须标记为“未验证”。

开发者职责：按验收步骤操作并反馈真实结果，不把构建成功替代为用户体验通过。

### 7. Git 提交与 PR

进入条件：用户已明确授权提交/推送/创建 PR，且测试、审查和验收结论可交付。

执行要求：确认分支、工作区和提交范围；使用清晰的 Commit Message；推送目标分支并在需要时创建 PR。不得自动合并 `main` 或 force push。

完成标准：提交内容只包含当前模块，远程状态和 PR 链接可追踪；若未获授权则保留本地修改并报告。

开发者职责：审阅最终 diff、提交信息和 PR 描述，确认后续审查人能复现验证结果。

### 8. 技术复盘

进入条件：模块已有测试与验收结论，且变更状态明确。

执行要求：记录关键技术决策、问题与解决方案、警告来源、未完成事项和可迁移知识；必要时新增 ADR。

完成标准：模块文档、测试结果和决策记录与代码一致，后续开发者可以据此继续工作。

开发者职责：确认复盘内容准确、简洁，并指出仍需人工判断的风险。

## 模块记录模板

每个模块至少记录以下信息，可放在任务报告、模块文档或 PR 描述中：

- 模块编号与目标
- 功能边界与明确非目标
- 核心接口与数据流
- 验收标准
- 实际测试结果
- 重要技术决策
- 实际完成状态：`planned`、`in progress`、`tested`、`accepted` 或 `complete`

只有在必要测试通过、人工验收完成或明确不适用，并且审查结论已记录后，模块才能标记为 `complete`。代码存在但未完成测试或验收时，最多标记为 `tested` 或 `in progress`，不能宣称正式完成。
